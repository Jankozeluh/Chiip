# Chiip — Architecture

> How the project is organized and which rules the code follows. Updated whenever a folder, system or convention is added.
>
> Last updated: 2026-10-16. The Godot project exists; the folders below are created, systems are added milestone by milestone.

## Engine

- Godot 4.7.2, standard edition, scripted in GDScript.
- Units: 1 Godot unit = 1 metre. Godot's Y axis points up and "forward" is −Z.

## Key project settings

Stored in `project.godot`. The reasons are in [DECISIONS.md](DECISIONS.md).

| Setting | Value | Decision |
|---|---|---|
| Renderer | Forward+ | D-008 |
| 3D physics engine | Jolt Physics | D-009 |
| Physics ticks per second | 128 | D-010 |
| Physics interpolation | On (jitter fix 0) | D-010 |
| Default gravity | 20.32 m/s² (CS `sv_gravity 800`) | D-011 |
| Window size | 1280 × 720 | — |
| Audio buses | Master (limiter), Effects (reverb), MuffledLight, Muffled and MuffledHeavy (low-passes into Effects), Interface, Music (`default_bus_layout.tres`) | D-058, D-190, D-192 |
| Main scene | `ui/main_menu.tscn` (the main menu); `main.tscn` is the game it starts | D-064 |

## Folder structure (planned)

The project is organized **by feature**: a scene and its script sit in the same folder. Unity projects often split by type instead, with separate Scripts/ and Prefabs/ folders.

```
Chiip/
├── project.godot      Godot project file
├── main.tscn / .gd    The game's root scene: pixelated world + HUD
├── default_bus_layout.tres  The audio buses: Master, Effects, MuffledLight, Muffled, MuffledHeavy, Interface, Music (D-058, D-190)
├── README.md          Start here: the player's guide (download, controls, playing with friends)
├── LICENSE            GPL-3.0, the code (D-170)
├── LICENSE-ASSETS     CC BY-NC-SA 4.0, art, models, maps and sounds, with the folders it covers
├── THIRD_PARTY_NOTICES.md  Godot, FuncGodot, Silkscreen: shipped inside every build
├── CONTRIBUTING.md    How to submit a map or code, and under which licence (D-176)
├── CHANGELOG.md       Every release's notes, newest first (the GitHub Releases' text, D-179)
├── site/              The website, plain HTML/CSS/JS, published to GitHub Pages (D-179); .gdignore keeps Godot out
├── .github/workflows/ pages.yml: publishes site/ on every push to main
├── CLAUDE.md          Working rules for Claude, including documentation rules
├── docs/              All documentation
├── addons/            Third-party Godot plugins only (func_godot)
├── assets/            Shared raw assets
│   ├── textures/      64 × 64 map textures drawn like the crew (tools/make_world_textures.py, D-140): the base set at the top,
│   │                  the kit's sets in industrial/, urban/, interior/, nature/ (D-121)
│   ├── materials/     One material per texture, world triplanar (for CSG geometry), in the same set folders
│   ├── environments/  Shared sky / fog / ambient settings
│   ├── models/
│   │   ├── crew/      Generated class models: .glb + albedo + team mask (tools/modelgen, D-072)
│   │   └── props/     Generated map-kit props: .glb + albedo (tools/modelgen props, D-122)
│   ├── sounds/        Every game sound, generated (D-020); `music/`: the menu theme and stingers (D-195)
│   ├── fonts/         Silkscreen pixel font (+ its OFL license text)
│   └── ui/            Pixel-art icons of the UI theme (generated, D-057)
├── characters/        Shared Character (movement + CS rules), input commands, controller base
│   └── crew/          The crew (M6): the team-colour shader, the model body, the class data (`class_data.gd`, `classes/*.tres`) and the preview
├── player/            The player: a Character variant with keyboard/mouse controller and camera
├── weapons/           Weapon logic, weapon data files (.tres), weapon scenes
├── bots/              Bot scene (a Character variant) and its AI controller
├── bomb/              The bomb of bomb rounds: scene and rules (M8, D-080)
├── net/               Multiplayer (M9): the session, the packets, the host's and the clients' game code
├── maps/              Test maps and playable maps
│   ├── comparison/    M3: the same room built with CSG and with TrenchBroom
│   ├── props/         Reusable map objects (target dummy)
│   ├── kit/           The map kit (M10): generated prop scenes (props/), lamp scenes (lights/), their scripts
│   │                  (kit_light, kit_bomb_site, kit_route_point, and the range entities' kit_weapon_stand and
│   │                  kit_text_sign), map_template.tscn, the generated kit gallery
│   └── fgd/           Chiip's func_godot entity definitions: a worldspawn that stores texture metadata (D-084),
│                      the kit's generated props and lamps (chiip_kit_fgd.tres, D-122), and the hand-written
│                      mapper entities: glass, fence, clip, bomb sites, spawns and other markers (chiip_mapper_fgd.tres, D-125),
│                      and the range entities for training maps (D-142)
├── ui/                HUD, scoreboard, menus, developer console, the UI theme (chiip_theme.tres) and its preview
├── systems/           Shared systems: teams, round manager, team respawn match and match settings, noise bus, surfaces, the sound mix, acoustics and music (M13), arena rules (practice), physics layers, the player's settings
├── shaders/           Shaders: palette effect, grid placeholder for blockouts, the viewmodel's projection (include)
├── tests/             Automated test scenes, run headless (D-018)
└── tools/             One-off tool scripts run from the command line (not part of the game)
```

## Scenes and files

| File | What it is |
|---|---|
| `main.tscn` + `main.gd` | Root (main) scene. `get_map()`, `change_map(path)` (console), `restart_match()` (reloads the current map in the current mode: the match-end screen's Play again). Loads the map from the `GameLaunch` description the main menu left (D-064), else from `map_scene` (default `maps/test_map.tscn`, or `-- --map <scene>` on the command line), puts it in the world viewport, adds the game rules and hands its `Player` to the HUD and overlay, and the round manager (if the rules are a match) to the match-end screen, which hides again whenever a map loads, and to the HUD (`set_round_manager()`: the round HUD with top bar, kill feed and banners; null in practice mode hides it, and the previous manager is dropped) and to the hold-Tab scoreboard (`Scoreboard.set_round_manager()`, null in practice mode = it never shows). Game rules by `mode` (`Mode.MATCH` by default, `-- --practice` for `Mode.PRACTICE`): a `RoundManager` with `match_settings` on maps with navigation and both team spawn groups, else an `ArenaRules` on maps with navigation, else none. Maps hold only the level; the rules node is added as a child of the map, named after its class. In a match it also turns on `PlayerController.spectating_enabled` and connects the controller's `view_target_changed` to the HUD (`_set_up_spectating()`). The world (test map + player) runs inside a `SubViewport` rendered at `Settings.pixel_height` lines (480 by default, scaled by whole numbers) and scaled up with nearest filtering; the HUD, debug overlay, scoreboard, class menu, pause menu, match-end screen, settings menu and console sit on top. `main.gd` gives the class menu the game rules and the player (`ClassMenu.set_rules()`, null rules in a free-roam map = it never opens) and its UI scale. `Settings.pixelate_hud` switches to rendering the whole window at the low resolution and `Settings.palette_effect` the color limit: `apply_pixel_settings()` reads them and runs when one changes (the old `pixel_height`, `pixelate_hud` and `palette_effect` exports are gone). `_ready()` loads the player's settings file (`Settings.load_from_disk()`) unless the `load_settings` export is off, which tests that load this scene use so they never touch the real file, or the main menu already loaded it (`Settings.is_loaded()`). Holds the `SettingsMenu` (`open_settings()`, `get_settings_menu()`, scaled with the other UI in `apply_pixel_settings()`) and the `PauseMenu` (D-065, `get_pause_menu()`: `_ready()` connects its `settings_pressed` to `open_settings()`, its `leave_pressed` to `return_to_menu()` and the settings menu's `closed` to `PauseMenu.settings_closed()`; `_spawn_map()` sets its leave text, "Leave match" with a `RoundManager`, "Leave practice" with `ArenaRules`, else "Leave"; scaled in `apply_pixel_settings()`). **Menu hand-over (D-064):** `_load_map()` first asks `GameLaunch.is_pending()`: if the menu left a description, that map, `Mode.PRACTICE` or `Mode.MATCH` and the `MatchSettings` are used (once: `GameLaunch.clear()`; the command line is ignored then); else the command line (`-- --map`, `-- --practice`; a match is the default, so `-- --match` needs no code here, it only makes the menu skip itself) and the exports as before. A practice arena gets `ArenaRules.bot_difficulty` from `match_settings.bot_difficulty`. `return_to_menu()` (the pause menu's Leave button, the match-end screen's Main menu button, console `disconnect`) sets `get_tree().paused = false` first (the pause belongs to the tree, so the next scene would start frozen) and then is `change_scene_to_file(GameLaunch.MENU_SCENE)`. `apply_pixel_settings()` is `PixelView.apply()` plus scaling the menus; `UI_DESIGN_HEIGHT` lives in `PixelView` |

## How the player camera works

Physics interpolation (D-010) draws the player's body smoothly between physics ticks. If the camera were a normal child of the body, mouse look would only be applied once per tick and then smoothed, which adds a small delay. Instead:

1. Mouse movement updates two angles (`_yaw`, `_pitch`) immediately in `_unhandled_input`.
2. Each physics tick, the body turns to `_yaw`, so movement keys follow your view.
3. Each rendered frame, `_process` places the camera at the head's *interpolated* position and applies the angles directly. The camera is `top_level` (ignores its parent's transform) and has interpolation off.

**Spectating (D-046).** In a match, when you are dead the same camera shows a teammate instead: `_process` takes the head's interpolated transform from `get_view_target()` (your own character, or the teammate being watched). For a teammate the rotation is that head's drawn rotation (their aim, smoothed between ticks like the position) instead of your mouse angles; the recoil kick is added from *their* weapon's `view_punch`. There is no new camera, so the crosshair, the audio listener and the HUD keep pointing at the same node. The teammate's `Body` and your own rifle (a child of the camera) are hidden meanwhile; the teammate's rifle stays, because a bot's rifle hangs under its `Head` at the same offset as your first-person rifle and so looks like their viewmodel. The state (who is watched, the 2 s / 1.5 s waits) lives in `PlayerController._physics_process` and only reads `team`, `is_alive()` and the head: it is presentation, so no game rule depends on it.

## TrenchBroom maps (being evaluated in M3)

1. Open the `.map` in TrenchBroom (game "Chiip"), edit and save.
2. Rebuild: select the `Map` node in Godot and click *Build Map*, or run `tools/build_maps.gd`.
3. Bake lighting: select `LightmapGI` and click *Bake Lightmaps* (editor only, it needs the GPU).

TrenchBroom axes become Godot axes as (x, y, z) → (y, z, x), divided by 39.37. A 64-pixel texture covers 64 units = 1.63 m, the same density as the CSG materials.

**Props from the map kit (D-122):** part lists live in `tools/modelgen/props.py` (palette, materials, helpers, crates, barrels, industrial, barriers, doors and windows, vehicles, signs), `props_urban.py` (urban, interior, nature, debris) and `props_lights.py` (lamps); `kit.py` writes them. Wall props (doors, windows, signs, wall lamps) have their origin on the wall face, ceiling lamps on the ceiling, everything else on the floor. A prop is a func_godot *point entity* whose definition (in the generated `maps/fgd/chiip_kit_fgd.tres`, included by `chiip_fgd.tres` through `base_fgd_files`) names a scene, `maps/kit/props/prop_<name>.tscn`. When the map is built, func_godot instances that scene at the entity's origin, turned by its angle (+180°, so angle 0 points the prop's front, its −Z, along TrenchBroom's +X). The scene is generated: a `StaticBody3D` (layer 1 for solid props, layer 3 for see-through ones, D-123) or a plain `Node3D` for decoration, with the `.glb` as `Model`, one `BoxShape3D` per box of the part list, and `metadata/surface` for `Surfaces`. The entity definition also names the `.glb` as TrenchBroom's display model (`model("assets/models/props/<name>.glb")`, scaled by the game config's 39.37), so the entity browser and the 3D view show the real prop. `tools/build_maps.gd` saves placed props as scene instances: it only hands the scene root ownership of nodes func_godot made itself, never of the nodes inside an instance.

**Mapper entities (D-125):** `maps/fgd/chiip_mapper_fgd.tres` (hand-written, included by `chiip_fgd.tres` after the kit) defines the brush entities `func_glass`, `func_fence`, `func_clip` (StaticBody3D on layer 3; the clip without a mesh) and `trigger_bombsite` (an `Area3D` on the triggers layer with `KitBombSite`), and the point entities `info_attack_spawn`, `info_defend_spawn`, `info_respawn`, `info_patrol`, `info_hold` (`Marker3D` nodes in the groups the game reads) and `info_route` (`KitRoutePoint`). At run time a bomb site renames itself `BombSite<letter>`, turns its brush shapes into one `BoxShape3D` named `Shape` and adds its `Letter`; route points move under a `Route_<name>` node (group `attack_routes`) in their `order`. So TrenchBroom-made maps and hand-placed markers look the same to the game. `tools/new_map.gd` makes a map scene from `maps/kit/map_template.tscn`. **Range entities (D-142)**, in the same file, for training maps: `range_target` (an instance of `maps/props/target_dummy.tscn`; `TargetDummy._func_godot_apply_properties()` takes `title`, `move_distance`, `move_speed`), `range_weapon` (`KitWeaponStand`: a `WeaponSpot` child with the chosen gun, put out again `refill_time` seconds after its `taken` signal), `sign_text` (`KitTextSign`, a `Label3D` in the pixel font, turned 180° at build time so it reads from the side its angle points to) and `info_bot_spawn` (a `Marker3D` in `bot_spawns` only).

**Lamps (D-124):** a lamp entity's scene (`maps/kit/lights/light_*.tscn`, generated like the props) has `KitLight` (`maps/kit/kit_light.gd`, a `@tool` script) on its root. Its exported values (kind, colour, energy, range, shadows, the light's offset, a spot's angle and tilt) build an internal `OmniLight3D` or `SpotLight3D` in `_ready()`; `_func_godot_apply_properties()` takes `light_color`, `light_energy`, `light_range` and `shadows` from the TrenchBroom entity when the map is built. Lights fade out beyond 45 m from the camera; shadows are off unless a mapper turns them on.

**Textures and materials (D-121):** TrenchBroom lists every image below `assets/textures/` and turns each folder into a collection (the base set at the top, then `industrial`, `urban`, `interior`, `nature`). A face's texture name is its path below that folder without the extension (`industrial/rust_plates`). When building, func_godot looks for a material with the same path and the extension `.tres` next to the image; if there is none it makes one from `assets/materials/map_default.tres` with the image as albedo. So a texture that needs something special (the chain-link's see-through holes: alpha scissor, both sides drawn) gets a hand-made `<name>.tres` beside its PNG. `tools/texture_report.gd` measures textures against the look rules. Every texture is drawn by `tools/make_world_textures.py` the way `tools/modelgen/paint.py` paints the crew (D-140): a base shade on a crew or prop ramp, a pattern with one-texel joints, little grain; `TABLE` lists them.

## How the screen is put together

The game moves between two scenes (D-064): the **main menu** (`ui/main_menu.tscn`, the project's main scene) and the **game** (`main.tscn`). The menu's Start and Practice leave a `GameLaunch` description in static variables and call `change_scene_to_file()`; `main.gd` reads it once in `_ready()`. The match-end screen's Main menu button and the console's `disconnect` change back with `Main.return_to_menu()`. The command-line shortcuts (`-- --match`, `--practice`, `--map`) skip the menu the first time. Both scenes load the settings if nobody has yet, apply the pixel settings the same way (`PixelView`) and use `MenuState` for the mouse.

```
MainMenu (Node, ui/main_menu.gd)
├── World (SubViewportContainer, like the game's)
│   └── SubViewport
│       ├── PaletteEffect (CanvasLayer)
│       ├── Flight (MenuFlight: Path3D → PathFollow3D → Camera3D)
│       └── TestMap (without its Player; added in code)
├── Page (CanvasLayer: the left column: CHIIP and its chips, Play / Practice / Settings / Quit, Host / Join, the build and the map's name)
├── MatchSetup (CanvasLayer, layer 2: the Play screen, hidden until Play)
├── LobbyMenu (CanvasLayer, layer 2, hidden until Host or Join; M9)
└── SettingsMenu (CanvasLayer, layer 6, hidden until Settings)
```

The game:

```
Main (Node, main.gd)
├── World (SubViewportContainer: stretch on, shrink = window height / 480 rounded, nearest filter)
│   └── SubViewport (853 × 480 on a 1440p screen, 640 × 360 in a 720p window)
│       ├── TestMap (map + Player)
│       └── PaletteEffect (CanvasLayer, optional full-screen color limit)
├── HUD (CanvasLayer)
│   └── RoundHud (Control: top bar, center messages, KillFeed; hidden in practice mode)
├── DebugOverlay (CanvasLayer)
├── Scoreboard (CanvasLayer, layer 3, shown only while Tab is held in a match; runs while paused)
├── PauseMenu (CanvasLayer, layer 4, hidden until Esc; runs while paused)
├── MatchEndScreen (CanvasLayer, layer 5, hidden until the match ends)
├── SettingsMenu (CanvasLayer, layer 6, hidden until opened: the pause menu's Settings button or the console command `settings`; runs while paused)
└── DevConsole (CanvasLayer, layer 10; runs while paused)
```

- **Menus and the mouse (D-059).** Anything that takes over the keyboard and mouse (the settings menu, the console, the main menu and match setup, the pause menu) registers with `MenuState` while it is open (`MenuState.open(self)` / `close(self)`). That one list decides everything: `PlayerController` ignores input while `MenuState.blocks_gameplay()`, the hold-Tab scoreboard stays hidden, the first menu to open shows the mouse and the last to close captures it again, and only the menu on top (`MenuState.is_top(self)`) reacts to Esc. A full-screen menu puts a `ColorRect` with `mouse_filter = STOP` behind its panel (like the match-end screen), so clicks never reach the player controls, and checks `visible` in `_input` (a hidden `CanvasLayer` still receives `_input`). Tree order matters for `_input`: later nodes are called first, so a menu goes *before* the console in `main.tscn` and the console, which is on top, sees Esc first. The order of Esc in the game: console, settings menu, match-end screen, pause menu (later nodes first), so each of the first three takes it when it is open or showing, and with none of them the pause menu does.
- **Pausing (D-065).** The pause menu opens with `get_tree().paused = true` and closes with `false`. Every node with the default process mode stops (the map with its characters, bots and weapons, the `RoundManager` and its timer, the HUD and kill feed, tweens bound to those nodes, `create_timer(…, false)` timers, the physics and navigation servers, playing sounds); the four scenes with `process_mode = Always` keep running: the pause menu, the settings menu, the console and the Tab scoreboard (it has to see `MenuState.blocks_gameplay()` to hide). **Rules:** game time is only ever counted in `_physics_process` / `_process` deltas (never wall-clock time) so a pause stops it; a timer made in code uses `create_timer(time, false)` or it keeps counting; a sound that must play while paused (a menu sound) is `PROCESS_MODE_ALWAYS`; scene changes unpause first (`Main.return_to_menu()`). Single-player only: in M9 the menu becomes an overlay that doesn't pause.
- The SubViewport renders the 3D world at low resolution, and the container scales it up with sharp (nearest) pixels.
- Sharp-HUD style: the window itself stays full resolution, so the HUD is crisp. Pixelated-HUD style: the window's *content scale* is set to the low resolution (`Window.content_scale_mode = viewport`), so everything is pixelated, HUD included.
- The HUD and overlay are laid out for a 1280 × 720 window and scaled with `UiScale` by the UI scale factor: the tighter of width / 1280 and height / 720, in half steps from 1.0 up (`PixelView.ui_scale_for()`, D-151), so the layout fits any window shape. The scoreboard, the pause menu, the match-end screen, the settings menu, the console and (in the main menu scene) the main page and match setup are *menus*: they get the same factor through their own `set_ui_scale()`, which hands them a copy of the UI theme scaled by it (`UiTheme.apply()`, D-057), so their fonts, borders, spacing and icons are exactly 1.5× at 1080 pixels. The round HUD is part of the HUD: `HUD.set_ui_scale()` passes the factor on, and `UiScale.apply_tree()` scales its containers. Since M10 (D-133) the HUD takes its look from the theme too: its labels, top bar, centre messages and bomb HUD pick `Hud*` roles built from the `HUD_*` tokens, and state colours (freeze timer, alert, notice, gold, dead pip) and the pip size live in a custom theme type `Hud` that the code reads (`get_theme_color("alert", "Hud")`). It is still scaled by `UiScale`, which reads the role's size and outline the first time and writes scaled overrides. `ui/hud.gd` and `ui/kill_feed.gd` keep their own colours until M7, which rewrites them, is merged.
- Mouse look uses `screen_relative`, so sensitivity is the same in both styles (checked: 2.200° for 100 counts).
- The pixel height, the HUD style and the palette effect are settings (`Settings.pixel_height`, `pixelate_hud`, `palette_effect`, D-058, and `ui_scale`, D-181): `main.gd` (and `MainMenu`) listen to `changed` and run `apply_pixel_settings()` (both through `PixelView.apply()`), so a change shows at once. The window's content scaling stays when the scene changes; the next scene applies it again. The player's field of view is a setting too (CS's horizontal angle across 4:3, default 90°, which is the 73.74° vertical the camera had).
- Text in the 3D world (`Label3D`) uses the pixel font with nearest filtering. Map signs are world-sized (`pixel_size` 0.04, about 0.32 m tall) and shrink with distance. Dummy titles and damage numbers use *Fixed Size* (the same size on screen at any distance) with `pixel_size` 0.004167, so one font pixel = one pixel of the 360-line world image.

## The UI theme (D-057)

Every menu takes its look from one `Theme` (`ui/chiip_theme.tres`, the project theme), so a menu is built from plain controls and a few *type variations* and needs no colors or sizes of its own.

- **Rules for a menu:** use a variation for a role instead of overriding a style; **no theme overrides of any kind** (colour, font, font size, constant, stylebox, icon; since M10 task 5 `ui_test` builds every menu and checks); a colour that depends on data picks a variation (`FriendlyScoreLabel` / `EnemyScoreLabel`, `VictoryLabel` / `DefeatLabel`) or reads a `Palette` colour (`dead_row`); a node's own `custom_minimum_size` is fine, `UiTheme` scales it. Scenes are laid out for a 720-pixel-tall window, and `set_ui_scale(factor)` is `UiTheme.apply(self, factor)` (rows or nodes added later: `UiTheme.apply_sizes()`).
- **Variations** (name → what it is): `Label`: `TitleLabel` (48 px), `ScoreLabel` (32), `HeaderLabel` (accent, a section title), `DimLabel` (secondary text), `BrightLabel` (white). `PanelContainer`: `ModalPanel` (accent frame, a screen that wants attention), `OverlayPanel` (see-through, over the game), `InsetPanel` (a sunken area), `ConsolePanel`, `RowPanel` and `YouRowPanel` (table rows), `TeamHeaderFriendly` / `TeamHeaderEnemy` (the colored team bar). `MarginContainer`: `PanelMargin` (16 / 12), `PanelMarginWide` (24 / 18), `RowMargin` (8 / 2). Boxes: `ContentBox` (8), `TableBox` (12), `TeamBox` (2), `ScoreRow` (14), `FormRow` (16), `ButtonRow` (24). `BigButton` (32 px, for the main menu); `TooltipPanel` / `TooltipLabel`. Added in M10 (D-131), today's look until the mockups: `HeroLabel` (the biggest text: the game's name, the match result), `ModeButton` with `ModeTitleLabel` / `ModeDetailLabel` inside and `ModeList` / `ModeText` boxes (the main menu's mode choice), `PrimaryButton` (the main button of a screen), `TextButton` (a word to click, no box at rest), `SegmentRow` (a segmented choice's strip), `PageMargin` and `ModeMargin`. Since task 8 (the mockups' Foundations, D-134): `BigButton` is a menu item (48 px, 32 px text, lime fill and the chip icon on hover or focus), `SmallItemButton`, `PrimaryButton` / `BigPrimaryButton` (lime fill, hard shadow), `SegmentButton` inside a `SegmentFrame` (the chosen one TEXT-filled), `ModeButton` (a Play-screen card), `MuteLabel`, `LargeLabel`, `FriendlyLabel` / `EnemyLabel`, `KeyCapLabel` / `DimKeyCapLabel`, `TagLabel`, `InkPanel` (a full-screen menu's background), `SidePanel` (the main menu's column), `RaisedPanel`, `PlatePanel`, `CardRow`; `TitleLabel`, `HeroLabel`, `VictoryLabel` and `DefeatLabel` use Silkscreen Bold. Since task 5: `FriendlyScoreLabel` / `EnemyScoreLabel` (scores in the team colours), `VictoryLabel` / `DefeatLabel` (the match result), `ConsoleLabel` / `ConsoleLineEdit` (the console's lines and input; since task 13 in the pixel font, with `ConsoleErrorLabel`, `ConsoleBox`, `ConsoleOutputMargin`, `ConsoleLines`, `ConsoleInputRow`, `ConsoleInputBox`), `SwatchRow` / `SwatchMargin` (crosshair colour swatches), `BackdropPanel` (the dim full-screen `Panel` behind a modal menu, which also stops clicks), and the `Palette` colour `dead_row` (a dead player's row is multiplied by it). The custom `Palette` type also holds `friendly_text` / `enemy_text` (team colours lightened for dark panels). Plain containers keep Godot's defaults on purpose (the HUD relies on them).
- **Controls styled directly:** Button, OptionButton (and MenuButton), CheckBox, CheckButton, LineEdit, HSlider, VSlider, ProgressBar, TabContainer, TabBar, HScrollBar, VScrollBar, HSeparator, VSeparator, PopupMenu, RichTextLabel (colors). Not styled yet: SpinBox, ItemList, Tree, TextEdit, dialogs (`Window`); add them when a menu needs one.
- **Tokens (D-131):** every colour, font, text size, line width, padding and spacing is a named constant in `tools/ui_palette.gd`; `tools/make_ui_theme.gd` only says which token goes where and has no numbers of its own (a `ui_test` check reads its source). The theme checks in `ui_test` compare with the tokens, not with numbers, so a new look doesn't break them.
- **Icon slots (D-131):** `UiIcons` lists 21 named icons (weapons, grenades, gear, bomb, classes, headshot, health). Drop `assets/ui/icons/<slot>.png` (drawn in 2 × 2 px cells, 16 × 16 next to body text) and rebuild the theme; screens ask `UiIcons.get_icon(self, &"headshot")` and show their text while it answers null.

Look at `ui/theme_preview.tscn`. `ui/chiip_theme.tres` is generated, so edits made in the editor are lost on the next run.
- **Scaling:** see D-057 and `ui/ui_theme.gd`. Icons are drawn in 2 × 2 px cells and sizes are multiples of 16 so they are crisp at 1×, 1.5× and 2×.

## How characters are controlled (M4)

```
Character (CharacterBody3D, character.gd)        ← simulates commands by CS rules
├── StandingCollision / CrouchingCollision
├── Head (eyes; tilts with pitch)
│   └── Camera3D + Weapon (player)  or  Weapon (bot, later)
└── PlayerController / BotController            ← produces one CharacterInput per tick
```

1. Each physics tick, `Character._physics_process` asks its controller for a `CharacterInput` (`get_input()`): the *pull* model guarantees the command is fresh for this tick.
2. The character applies it: it faces `yaw`, tilts the head to `pitch`, sets `weapon.trigger_held` and reloads, then moves, jumps and crouches by the CS rules.
3. The player's controller reads keys in `get_input()` and the mouse in `_unhandled_input()`; its camera follows the head every rendered frame, so mouse look stays instant.
4. A bot's controller fills the same command from its AI (walking: movement keys toward the next path point); in M9 a network controller will fill it from packets. The character can't tell the difference.

## How a round works (M5)

```
Map (test_map.tscn)
├── Player, markers (attack_spawns, defend_spawns, patrol_points), geometry …
├── Tactics                 ← hold_points (Marker3D) and attack_routes (Node3D → Marker3D waypoints)
├── RoundManager            ← added by main.gd; owns the game state
└── Bot1 … Bot5             ← added by the RoundManager (teammates and enemies)
```

1. `RoundManager` starts the match at the end of its first frame (so the map's navigation and markers are ready): it puts you on `player_team`, adds the bots and picks which team attacks.
2. Each round: everyone `respawn()`s on their side's markers, `Character.frozen` is set, and the phase runs `FREEZE` (5 s) → `LIVE` (1:55) → `ROUND_END` (5 s) → the next round (or the end of the match, see 7). Timers count down in `_physics_process`, never with `Timer` nodes, so they advance with the 128 Hz simulation (ARCHITECTURE rule 3).
3. Right after the respawns, `BotTactics.plan_round()` gives every bot its orders for the round (attack along a route, or hold a spot); during freeze time they can't act on them yet.
4. Freeze time is applied inside `Character`, to whatever its controller sends, so the player, bots and later network players are all held by the same rule.
5. The round manager listens to every participant's `damaged` and `died` signals for the stats and the kill events, and checks for an elimination at the end of the frame (`call_deferred`), so two last players killing each other in the same tick both count.
6. The HUD, kill feed and scoreboard only connect to its signals and read its state (the scoreboard just reads it every frame while Tab is held, D-050): in M9 the host runs it and clients show what it announces. The round HUD (`RoundHud`, D-047) reads `phase`, `time_left`, `score` and the alive counts every frame for the top bar, and builds its messages from `phase_changed`, `round_ended`, `sides_swapped` and `character_killed`; `main.gd` hands it the manager (or null) on every map load.
7. The match: first to `rounds_to_win` rounds (5, 10 or 15). `_end_round()` adds the round to `score[winner]` *before* emitting `round_ended`. When the `ROUND_END` pause is over, `_after_round_end()` decides what comes next: if a team has `rounds_to_win`, it freezes everyone, sets `winner`, enters `MATCH_END` and emits `match_ended(winner)`, and nothing happens after that; otherwise, if the round just played was number `rounds_to_win − 1`, it flips `attacking_team` and emits `sides_swapped`, and then the next round starts. After the flip each team spawns at the other end; team numbers, colors and stats don't change. The longest match is `2 × rounds_to_win − 1` rounds, so there is no draw.
8. `MatchEndScreen` (in `main.tscn`, above the HUD) listens to `match_ended`, reads `score` and, through its `ScoreboardTable`, `get_members()` and `get_stats()`, and shows the result. Its buttons only emit signals; `main.gd` restarts the map or quits.
9. Spectating doesn't touch the round manager: `PlayerController` notices your own death (`died`) and your respawn at the next round start (`on_respawned()`), and the HUD follows its `view_target_changed` signal (D-046).
10. **Bomb rounds** (D-080): on a map with `bomb_sites` areas (and `MatchSettings.bomb_rounds` on) the round manager adds a `Bomb` (`bomb/bomb.tscn`) to the map at the match start. At every round start, after the respawns, `Bomb.start_round()` gives it to a random attacker; `Bomb.active` is on only in the live round. The bomb reads each character's `is_holding_use()` (from `CharacterInput.use`): a carrier inside a site plants, a defender within 1.5 m defuses, and meanwhile `Character.busy` blocks moving and shooting the way `frozen` does. Its `planted`, `exploded` and `defused` signals reach the round manager, which stops counting `time_left` after the plant, ends the round with `EndReason.BOMB_EXPLODED` / `BOMB_DEFUSED`, and after a plant ends it by elimination only when the defenders are all dead. `BombHud` (in `hud.tscn`) reads `RoundManager.bomb` every frame and listens to its `picked_up`, `dropped` and `planted` signals. Bots find the bomb through its group `bomb`.
11. Classes (D-078, D-099): when the match starts the round manager drafts two classes for everyone (`get_draft()`, `is_drafted()`, signal `class_drafted`; bots take the one their team has fewer of) and answers `request_class()` (freeze time only, a drafted class only; `MatchSettings.class_draft` off gives M6's rules). The class menu and the console ask it and show the result; a class change swaps the character's body but is otherwise invisible to the round (hit zones follow the new body, so the stats and kill events keep working).


**Money (M7, D-098):** the `RoundManager` keeps everyone's money (`get_money()`, `add_money()`, `spend()`), pays rounds in `_end_round()` (winners `win_money`, losers by their losses in a row), kills in `_on_died()` (the weapon's `kill_reward`), the plant and the defuse in the bomb's handlers, and resets everyone at the match start and half time; it announces every change with `money_changed`. The HUD and the Tab scoreboard only listen. `has_economy()` is false in a `RespawnMatch`.
## Map rotation (M8, D-087)

- Match setup stores `match_mode`, `match_kill_limit` and `match_rotation` in `Settings`' `[match]` section; `GameLaunch.match_settings_from()` turns them into `MatchSettings.game_mode` and `kill_limit`, and `MatchSetup.get_rotation_maps()` gives the rotation (`GameLaunch.rotation_maps(start)`: `ROTATION_MAPS` = Depot, Square, Spillway, turned to start on the chosen map) or nothing.
- Start passes it on: `GameLaunch.start_match(map, rules, maps)` sets `GameLaunch.rotation`; `main.gd` copies it in `_take_launch()` (or builds it for `-- --rotation`) and keeps `_rotation` and `_rotation_index`.
- On every map load `main.gd` tells the end screen what comes next (`MatchEndScreen.set_next_map(title)`, "" hides the button). The button's `next_map_pressed` calls `main.next_map()`, which moves the index and calls `change_map()`, the same path Play again takes. The rules (`match_settings`) stay the same for every map.

## Team respawn mode (M8, D-082)

`RespawnMatch` (`systems/respawn_match.gd`) **is a** `RoundManager` with one long round, so everything that shows a match (round HUD, kill feed, Tab scoreboard, match-end screen) works unchanged; `score` holds kills. `main.gd` adds it instead of a `RoundManager` when `MatchSettings.game_mode` is `TEAM_RESPAWN` (`-- --respawn`), with spectating off.

The round manager runs a fixed sequence and asks a few overridable methods for the decisions a mode makes (the *template method* pattern):

| Hook | Rounds (`RoundManager`) | Team respawn (`RespawnMatch`) |
|---|---|---|
| `_add_bomb()` | adds the bomb on maps with sites | nothing |
| `_plan_bots()` | `BotTactics.plan_round()` | the bots' respawn-mode orders |
| `_round_duration()` | `round_time` (1:55) | `time_limit` (10:00) |
| `_live_tick(delta)` | nothing | counts down respawns and brings the dead back at `pick_spawn()` |
| `_clock_stopped()` | after the plant | in overtime |
| `_on_time_up()` | the defenders win the round | the leader wins, or overtime on a tie |
| `_score_kill()` / `_score_round()` | nothing / +1 round for the winner | +1 for the killer's team (enemy kills, live phase) / nothing |
| `_check_elimination()` | a wiped team loses the round | nothing (nobody stays dead) |
| `_after_round_end()` | next round, half time or match end | match end |

`is_team_respawn()` tells views which texts to use. `RespawnMatch.overtime` and `overtime_started` mark overtime.

**Bots** (D-083): `_plan_bots()` calls `BotTactics.plan_hunt()` once per team, which groups the bots and returns the team's `HuntPlan` (groups, roam points, the latest sighting, each group's goal). The `RespawnMatch` keeps the plans, advances their clock in `_live_tick()`, and after every respawn gives the bot its hunt order again (`BotController.hunt(plan)`; respawning resets a bot's orders to patrol) and notes the respawn (`HuntPlan.note_respawn()`, which decides who leads). Bots read the plan and report their sightings to it every tick they see or hear an enemy.

## Sound

- **Your own** footsteps and gunshots play through `AudioStreamPlayer` (no position, both ears). **Everyone else's** play through `AudioStreamPlayer3D`, from where they are (D-038). Their levels and ranges are `SoundMix`'s (below). `Character.is_local_player()` decides which, through `CharacterController.is_local()`.
- The 3D listener is the player's camera inside the world `SubViewport` (`audio_listener_enable_3d` is on). While you spectate a teammate that camera sits at their head, so you hear from where they are, as in CS; no sound routing changes.
- Footsteps play only for loud steps (running). Walking and crouch-walking are silent, matching what bots can hear (D-035).
- **Buses (D-058, D-190).** `default_bus_layout.tres` has Master (limiter), Effects, MuffledLight, Muffled, MuffledHeavy, Interface and Music. `Settings` sets the volumes of Master, Effects, Interface (and Music, D-195) from the 0 to 1 sliders (`linear_to_db`; 0 mutes the bus).
- **The mix (M13, D-190).** Every game sound plays through `Acoustics.play(player, stream, category)` (from a position) or `Acoustics.play_2d()` (your own), which set the player's volume, range, panning and bus from `SoundMix.TABLE` first. **A new game sound** picks a category (or adds one to the table) and plays through these; it never sets `volume_db`, `unit_size`, `max_distance` or `bus` itself. Menu sounds use `UiSounds` on Interface.
- **Surfaces** (D-084): `Surfaces.floor_kind(world, feet)` casts a short ray down and reads the hit brush's texture from func_godot's `func_godot_mesh_data` metadata (`texture_names`, `textures`, `normals`, `collision_shape_to_face_indices_map`), which Chiip's worldspawn class (`maps/fgd/chiip_worldspawn.tres`) stores on every built map body. `Character._play_footstep()` plays `Surfaces.footstep_sound(kind, footstep_sound)`; `Weapon._play_impact_sound()` sets the stream of the impact scene's `Audio` player (`impact_*`, `hit_body`, `hit_head`). Without the metadata (CSG maps) everything is hard. Since D-121 `Surfaces.kind_for_texture(name)` decides the kind: the three original names, then words in the file name (`metal`, `steel`, `plate`, `grate`, `rust`, `corrugated` → metal; `wood`, `plank`, `parquet`, `siding` → wood; `gravel`, `dirt`, `grass`, `ground` → gravel), so new textures need no code. Kit props carry a `surface` metadata entry on their body instead (D-122).
- **Interface sounds** (`UiSounds`, a static class): `attach(menu)` gives every button a hover tick and a click; `play(stream)` plays through one `AudioStreamPlayer` on the *Interface* bus that it adds to the tree root. The bomb HUD plays the planted alert. Off in headless runs.
- **Music** (`Music`, a static class, M13 D-195): `play_menu()` (the main menu calls it; fades in, keeps playing across menu scenes) and `stop()` (`main.gd` calls it when a game starts; fades out) for the looping menu track, `play_stinger(stream)` for the stingers; `stinger_for_round(won, reason)` and `stinger_for_match(won)` pick them (the round HUD and the match-end screen call these). Two `AudioStreamPlayer`s on the *Music* bus, added to the tree root (`PROCESS_MODE_ALWAYS`). Off in headless runs. The menu track loops through its import setting (`menu_theme.wav.import`: `edit/loop_mode=2`).
- **The bomb** (D-080) plays its beep, the plant key presses, the defuse clicks and the explosion through `AudioStreamPlayer3D`s on the bomb, by `Acoustics.play()`. The sounds are generated by `tools/generate_sounds.gd`.
- Tests set `footstep_sound = null` and use silent weapon data: headless runs have no audio device. The bomb test sets the bomb's four sound exports to null.

## How a character and its weapon work together

- **Several weapons, one in hand (M7, D-094):** a character's `Inventory` (child node `Inventory`) carries a primary, a pistol, the knife and grenades as `Weapon` nodes under the same parent as the scene's own weapon (the camera or the head). `Character.weapon` is the one in hand; the others are hidden with `process_mode` disabled. `Character.weapon_changed(weapon)` tells whoever follows the weapon in hand to reconnect: the HUD, the body (`CrewBody`, which also swaps the gun model on its weapon bone) and the bot brain. Weapons are made with `Weapon.create(data)` from the generic `weapons/weapon.tscn`. Switching goes through `CharacterInput` (`weapon_slot`, `last_weapon`, `drop`, a press of `use`), so bots follow the same rules. Guns on the floor are `WeaponPickup` nodes (group `weapon_pickups`): no collision, only the model; walking over one takes it into a free slot.
- **Reloads (M11, D-158):** `Weapon.get_reload_progress()` (0 to 1; a shotgun's current shell, below 0 while it's brought up) drives everything on one timeline: the reload sounds and `reload_cue(step)` (`GunModel.MAGAZINE_SOUNDS` / `SHELL_SOUNDS`), and the gun's `Magazine` and `Shell` following the left hand (`GunModel.update()`; the arms do it in their skeleton's `skeleton_updated`, the body in `_process`). Every reload clip is keyed to the same moments (`GunModel.MAGAZINE_EVENTS` / `SHELL_EVENTS` = `holds.RELOAD_EVENTS`). The body stretches a reload clip by its own length; a shotgun's first shell plays `reload_shotgun`, later ones `reload_shell`; `reload_finished` fades a reload still showing out.
- **Animation sets (D-096):** `WeaponData.anim_set` (the id when empty; the three grenades share `grenade`) names the clips a weapon uses: the body's `Hold` transition picks that set's aim blend (`Aim_<set>`), `FireKind` the rifle's or the pistol's kick, `Attack` a knife slash or stab or a grenade throw or lob, `ReloadKind` the weapon's reload (a shotgun plays `reload_shell` per shell, on `Weapon.shell_loading`); the first-person arms play `fp_<set>_<action>` (the rifle keeps `fp_<action>`), stretched to the draw or reload time. `WeaponData.hold_offset` places a knife or grenade model in the fist.
- **Kinds of weapons (D-095)** are branches on the data, not subclasses: `Weapon` fires `pellets` rays per shot, loads `reload_per_shell` guns shell by shell, steps a scope through `zoom_levels` on fresh presses of `aim_held` (set by the character from `CharacterInput.aim`, like `trigger_held`), and runs `_melee()` for a weapon with a `melee_range`. Scoped, `Character.get_max_speed()` uses the scoped speed, `PlayerController` narrows the camera (`get_zoom_fraction()`) and the mouse, and the HUD shows `ScopeOverlay`. Class perks are read through `Weapon._class_factor()` (reload, scope-in, scoped recovery).
- The player's weapon scene sits under the camera, so the first-person model follows the view. Bots' weapons sit under their `Head`; their viewmodel is hidden (`Character.set_first_person(false)`) and their body shows its own third-person gun on the hand, until a spectator looks through their eyes (M6, D-076).
- The character sets `weapon.trigger_held` from the command. The character processes first and its children after, so the weapon sees the new value in the same tick.
- The weapon sets the character's top speed (`Character.get_max_speed()`).
- The click that recaptures the mouse, and clicks while the mouse is free, never fire (`PlayerController`).
- Shots start at `Character.get_eye_position()` and use `Character.get_aim_angles()`, the aim *without* recoil kick. The ray tests world + hitboxes only, and excludes the shooter's own hit zones (`Character.get_hitbox_rids()`), since it starts inside their head, and, with friendly fire off (`Teams.friendly_fire`), the hit zones of every living teammate, so bullets pass through them as in CS. With friendly fire on, teammates are hit and `Character.take_damage()` scales their damage to a third.
- Bots aim at and look for the centres of the target's hit zones (`Character.get_head_position()`, `get_chest_position()`, `get_visibility_points()`), not at the eye position, because every class has CS's eye height but its own height (D-074).
- Damage path: weapon → `Hitbox.receive_hit()` (zone multiplier) → `hit` signal → `Character.take_damage()` → `damaged` / `died` signals → HUD, and later kill feed and rounds.
- Recoil has two parts. `Weapon._get_shot_direction()` adds the spray pattern offset to the aim. `Weapon.view_punch` (half the pattern, smoothed every frame) is added to the camera rotation in `PlayerController._process`. The aim itself never changes, so the view returns to it as recoil wears off.
- When a ray hits a `Hitbox`, the weapon computes `damage × range_modifier^(distance / 500 units)` and calls `Hitbox.receive_hit()`, which applies the zone multiplier and emits `hit` to whoever owns the hitbox (the dummy now, bots in M4).
- The viewmodel moves with the camera because it's a child of it. Shot kick is a tween back to the rest pose; the reload dip is computed every frame from the reload progress. Viewmodel meshes don't cast shadows. **Its own layer (M11, D-155):** every mesh in a `Viewmodel` draws with a viewmodel shader (`Viewmodel.prepare()`, called by `Weapon.set_arms()`), which gives it its own field of view (`Viewmodel.FOV`) and the nearest 2 % of the depth buffer, so it never pokes into walls. A new mesh in the viewmodel needs `Viewmodel.prepare()` too.
- Bullet holes are parented to whatever was hit, so they move with moving targets. Each weapon keeps its last 100.

## Testing

Run **all** the checks with one command from the project folder (the standard way, D-066):

```
bash tools/run_tests.sh
```

`tools/run_tests.sh` runs every suite one at a time, each as its own headless Godot run with its own `--quit-after`, counts the PASS and FAIL lines of each and prints a summary table (suite, pass, fail, status, seconds). It exits with the number of failed suites, so 0 means everything passed. A suite counts as failed when it prints a FAIL line, **no PASS line at all** (a parse error makes a suite exit with code 0 and print nothing, which looks like a pass), a `SCRIPT ERROR`, never reaches its final "All checks passed." line (the `--quit-after` safety net ended it) or exits with a non-zero code. A plain `ERROR:` line is not a failure: the settings suite prints one expected "ConfigFile parse error" from its unreadable-file check. `bash tools/run_tests.sh round ui` runs only the named suites, and each suite's full output stays in `$TMPDIR/chiip-tests/<name>.log` until the next run. The script needs only bash 3.2 and the Godot binary (no `timeout` command, which macOS lacks), and it never runs `--import` or touches git.

## Exporting (D-086, D-172)

- `export_presets.cfg` holds three presets (M12): **macOS** (a universal `.app`, ad-hoc signed, `builds/macos/Chiip.app`), **Windows** (x86_64, `builds/windows/Chiip.exe`) and **Linux** (x86_64, `builds/linux/Chiip.x86_64`); the last two embed the data in the one file. `builds/` is gitignored and has a `.gdignore`, so Godot never imports a build. `tests/*` and `tools/*` are excluded from every export, and each preset's include filter lists the licence files (`LICENSE`, `LICENSE-ASSETS`, `THIRD_PARTY_NOTICES.md`, the font's and the addon's licence): they are not resources, so without the filter the Licences screen would find nothing. `tests/release_test.gd` checks the presets (platforms, architectures, filters, versions, no secrets).
- `tools/package_release.sh` zips the three builds for a GitHub Release (a folder per system with the game and the three notices); `tools/release_notes.sh <version>` prints a version's notes from CHANGELOG.md; the whole routine is docs/RELEASING.md. The website (`site/`, D-179) reads GitHub's releases API in `js/site.js` and is published by `.github/workflows/pages.yml`.
- Exports need the export templates of the exact engine version (`~/Library/Application Support/Godot/export_templates/4.7.2.stable/`) and, for Apple Silicon, `rendering/textures/vram_compression/import_etc2_astc`.
- In an exported game text scenes and resources are converted to binary and reached through `.remap` files: code that lists `res://` folders must use `ResourceLoader.list_directory()` (the console's `map` list does).
- `tools/frame_timing.gd` measures frame times of a real match (in the editor build). See "Performance" below.
- **Shooting is checked in the export (v0.1.1, D-159):** `systems/hit_check.gd` (`HitCheck`, added by `main.gd` for `-- --check-hits`) starts practice on the range, puts an enemy bot 5 m ahead and fires once each way, prints `Chiip hit check: PASS` or `FAIL` and quits with 0 or 1 (`quit_when_done`, signal `finished`; `release_test` runs it too). Exported builds can't run `--script`, so this is the way into one. `tools/check_export.sh` exports a macOS release build into a temporary folder (or takes `APP=<.app>`) and runs it; `tools/package_release.sh` runs it on `builds/macos` first.
- **Exported packed arrays need typed defaults:** `@export var x: PackedStringArray = PackedStringArray()`, never `= []`. With an Array literal the export's text-to-binary conversion dropped the stored values (v0.1.0's empty hit zones); `release_test` rejects the pattern. The export caches conversions by a file's content, so after fixing a script, change the resource files too (or delete `.godot/exported/`) before exporting.

## Performance (M11, D-165 to D-169)

**Budgets.** A physics tick has 7.8 ms (128 Hz); a frame on a 120 Hz display has 8.3 ms. A 5v5 uses about 1 ms of CPU per frame on an Apple M5 (physics with the bots and animation trees about 0.8 ms, scripts 0.1 ms), and a LAN host about 0.3 ms more.

**Measuring** (`tools/frame_timing.gd`):
- **With a window:** the frame rate and each frame's parts (physics, scripts, drawing, the rest), the frames whose CPU part goes over 8.33 ms, the spikes with what was added to the scene in that frame, and the pipelines compiled while drawing.
  - On macOS with V-Sync off, the system sometimes holds a frame while waiting for the display. These are the 12–17 ms "draw" spikes, which players with V-Sync on don't get; `--vsync` measures with it on.
  - Metal reports no GPU times. A window that is covered, or on another Space, is slowed down by macOS, so check that the run had focus and keep other GPU work away.
- **Headless** (`--headless --fixed-fps 128 --spike 4`): the CPU side, about a minute of play in ten seconds of wall time. Best for finding hitches.
- **LAN host** (`--lan <scene>` with the menu's `--host --start 2 --no-settings --port <n>`): the tool starts a headless client itself.
- **`perf_test`** has the limits (see Testing).

**Rules for code that runs often** (every tick, every snapshot, or for every character at a round start):
- Never `load()` or list resources there. `WeaponData.all()` reloads every weapon file whenever nothing holds them, so keep what you need in a `static var` (as `Shop` and `NetProtocol` do).
- Don't search children for the same node every tick: keep it (`LagCompensation` keeps each zone's box as metadata).

## Code rules

- **Static typing everywhere**, e.g. `var speed: float = 6.0` and typed function signatures. Godot then catches mistakes early and autocomplete works better.
- **Documented code.** Every script starts with a `##` doc comment that explains its purpose. Exported variables and public functions get `##` comments too. Godot shows these in its built-in help (F1), so the documentation is visible inside the editor.
- **No magic numbers.** Gameplay values are `@export` variables or stored in Resource data files, so they can be tuned in the editor.
- **Signals for "something happened"** (e.g. `died`, `round_ended`), and direct function calls for "do this".
- **Keep multiplayer possible** (it comes in M9, D-033). See the next section.

## Keeping multiplayer possible

Multiplayer is added in M9, after the single-player game. These rules for M4–M8 keep that retrofit manageable:

1. **Characters only move and shoot through input commands.** A `Character` never reads the keyboard; a controller (player, bot, later network) gives it a `CharacterInput` each tick.
2. **Game rules live in "authority" code, separate from what's shown.** Damage, deaths, round state, money and the bomb are decided by gameplay nodes and announced with signals. HUD, sounds and effects only react to those signals. In M9 the host runs the rules, and clients just show the results.
3. **Gameplay runs in `_physics_process`**, at a fixed tick (128 Hz). `_process` is only for visuals (camera, effects, UI).
4. **Randomness that affects gameplay uses seeded generators** (like `Weapon.rng`), never the global `randf()`. Visual-only randomness (spark directions, hole rotation) can stay global.
5. **Characters and other gameplay objects get stable IDs**, so the host and clients can refer to the same thing.
6. **Settings are local, never game rules.** `Settings` (sensitivity, FOV, video, audio, crosshair, keys) is each player's own preference on their own computer. Nothing in a match (damage, rounds, spawns, bot behaviour) may read it, so the host never needs to send or check it; only presentation and the local controller do.
7. **Pausing is single-player only** (D-065). The pause menu stops the game with `get_tree().paused`, which nobody can do to a host's clock or to other players. In M9 it becomes an overlay that doesn't pause: it keeps its `MenuState` registration (so the local player still can't move or shoot while it is open) and stops touching `paused`. Keep gameplay free of anything that assumes the pause (it counts time only in `_physics_process` deltas), and the switch is small.

## Multiplayer (M9)

The decisions are D-100 to D-112. In short: the host runs the single-player game as it is; clients send their commands and show the host's snapshots; each client predicts its own player.

**The session** (`net/net_session.gd`, `NetSession`, D-101, D-102). One node per computer while it is online: `NetSession.open(tree)` adds it to the tree root (it survives scene changes; it is not an autoload), `host_game(name, port)` or `join_game(address, name, port)` connects, `close()` leaves and frees it. It talks through its own `multiplayer` (Godot's `SceneMultiplayer` with an `ENetMultiplayerPeer`, two ENet channels: 0 reliable, 1 unreliable).

**The transport** (`net/net_transport.gd`, `NetTransport`, D-114). The session doesn't make its connection itself: its `transport` does (`EnetTransport`, `net/enet_transport.gd`, by default; set another before `host_game()` / `join_game()`). A transport's `host(port, max_clients)` and `join(address, port)` make its `peer` (a `MultiplayerPeer`); `configure_connection(peer_id)` sets up each new connection (ENet: 3 to 8 s timeouts, throttle off), `flush()` sends what is queued (before a goodbye or a refusal), `get_ping_ms(peer_id)` and `disconnect_later(peer_id)` (after what is queued) do the rest. Nothing else in the game names ENet. A Steam transport (deferred, D-114) would make GodotSteam's `SteamMultiplayerPeer` from a lobby instead of an address.

- **Peer ids:** the host is 1, each client a random number (`local_peer_id`).
- **The roster** (`get_players()`: peer id, name, team, in join order) belongs to the host. A client says hello (`_rpc_hello`, with `NetProtocol.VERSION`; another version is refused), the host adds it with a unique, cleaned name (at most 16 characters, valid as a node name, never a bot's "Bot3") on the smaller team and sends everyone the whole roster (`_rpc_roster`). `request_team(team, limit)` asks the host for a team. `roster_changed`, `player_joined`, `player_left`, `joined`, `join_failed`, `closed(reason)`.
- **Match messages:** `send_to_all(dict)` (host → everyone, and itself) and `send_to_host(dict)` (client → host, with `"from"` added) arrive as `match_message`. RPCs, reliable, in order with the roster.
- **The game stream:** `send_packet(peer, bytes, reliable)` (peer 0: everyone) and `packet_received(peer, bytes)`. Packets are typed by their first byte (`NetProtocol.Message`: commands, snapshots, events, requests); events and requests are reliable. Every received packet waits in an inbox and is handed out at the start of a later physics tick (the session's `process_physics_priority` is -1000, so before any game code). Fake lag (`fake_lag_ms`, plus `fake_jitter_ms`) adds whole ticks; fake loss (`fake_loss`, 0 to 1, seeded `rng`) drops unreliable packets only; reliable packets keep their order. Counters: `packets_sent`, `packets_received`, `bytes_sent`, `bytes_received`, `packets_dropped`; `get_ping_ms()` is ENet's round-trip time.
- **ENet timeouts** are 3 to 8 s on both sides, so a lost connection is noticed quickly.

**Testing in one process** (`tests/net_harness.gd`, `NetHarness`, D-111): `add_side(name)` makes a branch of the tree with its own `SceneMultiplayer` (`SceneTree.set_multiplayer(api, branch_path)`), `start_host()` and `start_client()` open sessions on new sides on a random port between 27600 and 27900, `wait_until(condition, max_ticks)` waits. RPCs find their node by its path below the branch (`NetSession` on every side), so a host branch and a client branch talk exactly as two computers would.

**An online match** (D-100, D-105). `main.gd` gets the session (`net_session`, from `GameLaunch.net_session` or set by a test before the scene enters the tree). The game scene, map and rules are the single-player ones; online adds one node to the map:

| | Host (`NetHost`, `net/net_host.gd`) | Client (`NetClient`, `net/net_client.gd`) |
|---|---|---|
| Round manager | runs the match; `autostart` off, `start()` once every client loaded (or after 15 s) | `replica = true`: decides nothing, filled in with `replica_start()`, `replica_join()`, `replica_set_state()`, `replica_round_started()`, `replica_round_ended()`, `replica_killed()`... which emit its usual signals; the clock counts down between updates |
| Bomb | the real one | `replica = true`: `apply_replica_state()` from every snapshot emits `picked_up`, `dropped`, `planted`, `defused`, `exploded`; it beeps and follows its carrier by itself |
| Your player (the map's `Player`) | the host plays as offline | `replica = true` (health and death from the host) |
| The friends | bot scene without `BotController`/`BotSenses`, with a `NetworkController`; `manual = true` (stepped per command, task 4); `RoundManager.extra_players` joins them before the bots | puppets |
| Everyone else | bots | puppets: the bot scene without brain or navigation, `remote = true` (`set_remote_pose()` places them; they only play footsteps), `replica = true`, `weapon.remote = true` |

- **Network ids** (`Character.net_id`, D-102): given by the host to every participant in join order once the match started (the host's player is 1). Character nodes are named after their players.
- **Events** (`NetProtocol.Event`, reliable, sent to every client that is in the match): `WELCOME` (to one client when it has loaded: its own id, every character as `[id, name, team, class, peer]`, the match's state, the scoreboard, everyone's health), `PHASE`, `ROUND_STARTED`, `ROUND_ENDED`, `SIDES_SWAPPED`, `MATCH_ENDED`, `OVERTIME`, `KILLED` (with the score: team respawn counts every kill), `DAMAGED` (with the health left), `RESPAWNED` (position and yaw), `STATS` (at most every 32 ticks, when something changed), `CLASS_CHANGED`, and for later tasks `CHARACTER_ADDED`, `CHARACTER_REMOVED`, `RENAMED`. A client ignores events until its welcome.
- **Snapshots** (`NetProtocol.pack_snapshot()` / `read_snapshot()`): every second host tick (`NetHost.SNAPSHOT_INTERVAL`), at the end of the tick (a `_LateTick` child with `process_physics_priority` 1000): the host tick; for the receiving client its own character at full precision and the number of its last command run; the phase, clock and overtime; the bomb; every character (id, flags, position, velocity in half floats, yaw and pitch in 16 bits, eye height in cm, health, magazine, reserve); the cosmetic effects of the last 6 ticks (shots with where they landed, reloads, numbered).
- **Order within a tick:** the session hands out the packets (priority -1000), then `NetHost` / `NetClient` (-100), then everything else, then `NetHostLate` (1000).
- **Requests** (client → host, reliable, `NetProtocol.Request`): `CLASS` (the class menu on a client calls the replica's `request_class()`, which sends it; the host's round manager decides and every client gets `CLASS_CHANGED`).
- **Two games in one tree** (the network tests): the `characters` and `bomb` groups hold the nodes of every game, so code asks `Character.all_in_world(node)` and `Bomb.find_in_world(node)` for those of its own world; spawn markers are taken from the round manager's own map.

**Commands** (D-103). On a client your player is `manual`: the engine's physics tick doesn't move it. Every tick `NetClient` takes your controller's command (or a test's `command_source`), packs the movement keys into 1/127 steps (`NetProtocol.quantize()`, so both computers simulate the same numbers), numbers it (`CharacterInput.tick`, from 1) with the moment it shows the others at (`view_tick`), and sends every command the host hasn't confirmed, at most 16 per packet (`NetProtocol.pack_commands()`, 19 bytes each; a second of them is kept). On the host the friend's `NetworkController.receive()` keeps only numbers it hasn't seen, and `NetHost` runs them at the start of every tick: the budget grows by one per tick (up to 8 saved), each `Character.step(command, delta)` spends one. `step()` is the same code as `_physics_process` (`_simulate()`), followed by the weapon's `step()`; with `effects` off (prediction's replays) it skips the weapon, the footsteps and the noise. The ack in each snapshot (`NetworkController.last_run`) confirms them, and `NetClient` drops the confirmed ones. A numbered command's shot seeds the spread with `hash([net_id, tick])` in `Weapon._get_shot_direction()`. Connections have ENet's throttle switched off (`EnetTransport.configure_connection()`).

**Puppets** (D-104). `NetClient` keeps each puppet's snapshots (`[host tick, NetProtocol.CharacterState]`, the last 32, late ones sorted in) and a `clock`: the host tick it believes it is, one tick further every tick and pulled 5% of the way to the newest snapshot's tick (it jumps when more than 16 ticks off). Every tick, before anyone moves, `_show_puppets()` poses every puppet (`Character.set_remote_pose()`) at the render tick, `clock - 6`: position, yaw (`lerp_angle`), pitch, eye height and velocity interpolated between the snapshots around it, stance and floor contact from the older one; past the newest snapshot it moves along its velocity for at most 13 ticks, the dead don't. The engine's physics interpolation smooths between ticks as for any body. Frozen, busy, health and ammo come from the newest snapshot. A `RESPAWNED` event carries the host tick of the first snapshot with the character at its spawn: older snapshots of it are dropped. Effects (shots, reloads) are numbered by the host, repeated in four snapshots (`NetHost.EFFECT_TICKS` = 8) and played once: `Weapon.play_remote_shot(hit, position)` (sound, flash, kick, recoil for a spectator, `fired` for the body's animation; the client traces the ray from the puppet's eyes again to find the surface for the hole and the impact sound, and skips the hole when the body it hit has moved on) and `start_remote_reload()`. Your own shots are never taken from the snapshots: your computer predicts them. A puppet's footsteps come from its own interpolated movement (`Character._physics_process` for `remote` characters).

**Prediction** (D-106, `NetClient`). After sending a command, `NetClient` steps your character with a copy of it (`Character.step()`, everything a tick does offline: movement, the weapon, footsteps) and keeps `[command, PredictedState]` (position, velocity, crouching, eye height, ground contact, magazine, reserve). `NetProtocol.quantize()` cuts the command to exactly what the packet carries first (movement in 1/127 steps, angles and view tick as 32-bit floats). When a snapshot arrives, `_reconcile()` drops the history up to its ack and compares the acked entry with the host's `OwnState`: ammo differences are added (`Weapon.correct_ammo()`) and passed on to the newer entries; a difference over `POSITION_TOLERANCE` (1 cm) or `VELOCITY_TOLERANCE` (0.05 m/s), or in crouching or ground contact, counts as a correction: `Character.set_predicted_state()` puts the character at the host's state (and tells its next tick whether it starts on the ground, `set_floor_contact()`), every newer command is replayed with `step(command, delta, false)` (movement only), and the jump between the old and the new position (up to 1 m) goes into `Character.view_offset`, which `PlayerController` adds to the camera and `NetClient._process()` lets fade with a 0.1 s time constant (CS's `cl_smooth`). `frozen` and `busy` come from the snapshot. `NetClient.predict = false` turns it off (the character then stands where the snapshots put it), `corrections` and `largest_correction` count it.

**Lag compensation** (D-107, `net/lag_compensation.gd`). At the end of every host tick `NetHostLate` calls `LagCompensation.record(tick, characters)`: for every hit zone its box's global transform, half size and whether its character was alive (the last 128 ticks). A friend's character has `Character.lag_compensation` set, so `Weapon._shoot_bullet()` calls `trace(shooter, from, to, passable_rids)` instead of the physics ray: the world is tested as it is (`intersect_ray`, world only); the boxes at `clamp_view_tick(command.view_tick)` (at most `MAX_REWIND` = 0.4 s back, never newer than the last record) are interpolated between the two records around it (`Transform3D.interpolate_with`) and tested with `ray_box()` (the slab test in the box's own space); zones of the shooter, of passable teammates, of characters dead now or dead then don't count. The result looks like `intersect_ray`'s (`position`, `normal`, `collider`, `shape`) plus `impact_position` / `impact_normal`, the same spot on the zone where it is now, for the bullet hole. The host's own shots and the bots' shots use the physics ray as offline.

**Menus online** (D-109). `main.gd` calls `PauseMenu.set_online()` and `MatchEndScreen.set_online(online, host)` on every map load. Online the pause menu never touches `get_tree().paused` (its `MenuState` registration still holds your controls); the end screen's Play again and Next map are the host's (`main.restart_match()` / `next_map()` call `NetLobby.start_match()`, a full new start for everyone) and its third button is "Lobby" (`return_to_menu()` on the host: `NetLobby.return_to_lobby()`) or a client's "Leave" (closes the session). The console's `_refuse_online()` turns away `god`, `noclip`, `mp_friendlyfire` and `map`; `disconnect` calls `main.leave_online()`; `status` prints `get_status_lines()` of the `NetHost` / `NetClient` (also shown in the F3 overlay, `DebugOverlay.net_game`); `net_fakelag` and `net_fakeloss` set this computer's session's fake lag and loss.

**Coming and going** (D-110, `NetHost`). `NetSession.player_left` → `_on_player_left()`: before the start the friend's character is removed (its slot gets a bot at the start); after it `hand_to_bot()` gives it a brain (a new `BotController` + `BotSenses`, made from their scripts, or its own idle brain back), clears `manual` and `lag_compensation` and renames it "Name (bot)" (`RENAMED`). A client that joins while the host's lobby is `in_game` gets the running match's start message (`NetLobby._on_player_joined()` → `NetSession.send_to()`); when its "loaded" arrives `_take_over_bot()` picks the newest bot of its roster team (else the other team), puts its `BotController` and `BotSenses` aside (renamed `IdleBotController` / `IdleBotSenses`, `PROCESS_MODE_DISABLED`, so `BotTactics` and the hunt plans see a player and nothing is freed under them), adds a `NetworkController` and renames the character after the player; with no bot left the client is refused (`NetSession.kick()`). The welcome then names the taken-over character as the client's own, and a character dead at the welcome dies at once on the client (`apply_remote_damage(0, …, 0)`). `NetSession.close()` on the host sends `_rpc_closing` ("The host ended the game."), flushes and closes `GOODBYE_TIME` (0.2 s) later; `NetHost` and `NetClient` drop their `session` reference on `closed` (a session freed while the host's game still read it every frame crashed the engine).

**The lobby** (D-108, `ui/lobby_menu.gd` + `net/net_lobby.gd`). The main menu's Host and Join items open `LobbyMenu` (Host hosts at once, Join focuses the address): the connect page (name, address, port: `Settings.online_*`) or, while a session is active (`NetLobby.find_session(tree)`: the `NetSession` at the root), the lobby page. Host game opens a session at the root (`NetSession.open(tree)`) and hosts; Join connects and waits for `joined` or `join_failed`. The lobby page follows the session's `roster_changed` and the `NetLobby`'s `info_changed`; the host publishes the info (`NetLobby.publish(summary, slots, map)`) when the page opens and whenever the match settings change (match setup opened from Match settings…, its Start button relabelled "Done" with `MatchSetup.set_start_text()`); the slots become the session's `team_limits`. Start match calls `NetLobby.start_match(map, GameLaunch.match_settings_from(settings), rotation)`; every computer's `NetLobby` then fills `GameLaunch` (with `net_session`) and changes to the game scene. Back from a match (`return_to_lobby()`, or the session ending: `GameLaunch.notice` says why) the main menu opens the lobby by itself. Leave closes the session at once (the host's goodbye takes 0.2 s: during it the old session is renamed `NetSessionClosing`, closes only its own connection, and the lobby keeps Host and Join off until it is gone). Its look is mockup 06 (D-137): the Lobby and Join pages share one page frame; **Trust (M12, D-180):** the host does not trust a client. `NetSession._on_peer_packet` drops packets from anyone who hasn't said hello, over 8 KB (`MAX_PACKET_BYTES_FROM_CLIENT`) or over 400 a second (`allow()`, counted per second of physics ticks; three seconds of that remove the client, `kick()`), and `HELLO_TIMEOUT` removes a computer that never introduces itself; the three `any_peer` RPCs start with `is_host()`, use `get_remote_sender_id()` and are limited (`MAX_MESSAGES_PER_SECOND`, `MAX_TEAM_REQUESTS_PER_SECOND`, `MAX_HELLOS`); `is_valid_message()` accepts only a few short plain entries; `_clean_name()` strips control and direction-changing characters; `NetHost._on_request()` checks shape, type, range and length; `NetProtocol.unpack_commands()` drops impossible angles and a weapon slot that doesn't exist. Objects are never decoded (`bytes_to_var`, not `..._with_objects`). `tests/netsec_test.gd` is the proof.

**Tailscale (M12, D-173):** the host's "Friends join at" shows its Tailscale address first (`LobbyMenu.tailscale_addresses()`: IPv4 in 100.64.0.0/10 out of `IP.get_local_addresses()`) with its port and a **Copy** button (`copy_tailscale_address()`: "address:port" to the clipboard, the button says "Copied" for 1.5 s), then the same-network addresses under "Same network" (`local_addresses()` no longer lists Tailscale's). A pasted "address:port" in Join by IP fills the address and port fields (`split_address()`). `address_source` (a Callable) replaces `IP.get_local_addresses()` in tests. Hooks for tests include `get_tailscale_box()`, `get_tailscale_text()`, `get_copy_button()`, `get_lan_label()`, `get_switch_team_button()`, `get_footer_facts()` (from `build_facts()`, which the host also publishes for the clients), `get_team_header_texts()` and `get_address_texts()`. Command-line shortcuts for two windows on one Mac: `-- --host`, `--join <address>`, `--name <name>`, `--port <port>`, `--start <players>` (the host starts the match by itself) and `--no-settings` (the menu and the game don't load, so don't save, the settings file).

**The arsenal online** (D-113, M9 phase B; M7's interfaces are in "Weapons, money and buying" above). Protocol 2:
- **Commands** carry two bytes of buttons (`BUTTON_AIM`, `BUTTON_LAST_WEAPON`, `BUTTON_DROP` besides M4's) and `weapon_slot`, 21 bytes each.
- **Snapshots:** every character's weapon in hand (`NetProtocol.weapon_index()`, an index into `WeaponData.all()`, 255 none) and armor, `FLAG_HELMET`, `FLAG_KIT`; the receiver's own weapon after the acked command; then the world objects (`EntityState`: id, `ENTITY_PICKUP` / `ENTITY_GRENADE` / `ENTITY_SPOT`, weapon, flags floating / resting, position, yaw): grenades in every snapshot, guns on the floor and spots in every fourth (`NetHost.PICKUP_SNAPSHOTS`, `Snapshot.has_pickups`).
- **Events:** `INVENTORY` (to one client: its weapons as [index, magazine, reserve] and the one in hand; after `Inventory.changed` or `ammo_scavenged`, at the end of the tick, and with the welcome), `GRENADE` (entity id, `Explosion.Kind`, position, from `Grenade.detonated`), `FLASHED` (from `Character.flashed`), `MONEY` (total, change, reason, from `money_changed`), `DRAFTED` (from `class_drafted`); `KILLED` carries the weapon of the killing hit (`last_damage_source`); the welcome carries everyone's money and draft. Request `BUY` (an item id) next to `CLASS`.
- **Host** (`NetHost`): follows each character's weapon in hand (`weapon_changed`) for the shot and reload effects; numbers world objects on first sight (`_entity_ids`).
- **Client** (`NetClient`): `_apply_inventory()` removes what the host doesn't carry, gives what it does (non-held weapons take the host's ammo), puts the list in the host's order (`Inventory.reorder()`: the grenade key takes the same first grenade on both), and keeps the weapon you took out unless it's gone; `_reconcile()` takes out the host's weapon when the acked command's differs and corrects the acked weapon's ammo; puppets carry only the weapon in hand (`_apply_puppet_state()`); `_apply_gear()`; world objects: copies made by `_make_entity()` with `replica` on (`WeaponPickup` and `WeaponSpot` don't fall or put out guns, `Grenade` doesn't fly or go off), grenades interpolated at the render tick (`_show_grenades()`), `_on_grenade()` plays the effect and makes a smoke's `SmokeCloud` with `rng.seed = hash(position)` as the host's grenade did. A `Weapon` asks its holder whether it is stepped by the network code (`manual`) or a puppet's (`remote`), so weapons made later by the inventory follow without flags of their own.
- **M7's code on a client** (`Character.replica`): `Inventory.handle_input()` skips drop and swap, `update_pickups()` isn't called, `_die()` drops nothing, `Weapon._throw()` makes no grenade; `RoundManager.request_buy()` / `request_class()` and `RespawnMatch.request_class()` ask the host (`buy_request`, `class_request`); `replica_set_money()` and `replica_drafted()` fill in money and drafts. `WeaponPickup.all_in_world()` scopes the pickup lookups (inventory, bots, the round manager's floor clearing) to one world, like `Character.all_in_world()`.
